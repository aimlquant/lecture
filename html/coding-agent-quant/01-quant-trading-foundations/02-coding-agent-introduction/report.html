    강의 상세 리포트

    코딩 에이전트란 무엇이고 퀀트 작업에서 무엇을 할 수 있는가

    답을 듣는 데서 그치지 않고 파일과 실행 결과를 함께 확인한다

    확인일 2026-08-25

    핵심 본편 · core

    코딩 에이전트는 말만 하는 AI가 아니라 작업을 이어 가는 AI다

    모델에 문맥과 도구와 반복 작업이 더해진다

    이 리포트에서 코딩 에이전트(coding agent) 는 사용자의 요청을 읽고 답변만 만드는 데서 멈추지 않고, 허용된 작업 공간에서 파일과 개발 도구를 사용해 결과물을 만드는 AI를 뜻한다. 초보자에게는 AI 모델 + 작업 문맥 + 도구 + 확인 반복이라는 네 부분으로 이해하는 것이 가장 쉽다.

    OpenAI의 Codex IDE 공식 문서는 에이전트가 편집기에 열린 파일과 선택한 코드를 문맥으로 사용하고, 파일을 설명하거나 고치며, 변경 내용을 같은 화면에서 검토할 수 있다고 설명한다. 더 긴 작업은 별도 환경에 맡긴 뒤 결과를 다시 검토할 수도 있다 (Codex IDE 확장 기능 공식 문서).

    대답 방법을 설명한다

    어떤 코드가 필요할지 글로 알려 줄 수 있다.

    작업 파일과 명령을 다룬다

    허용된 폴더에서 파일을 만들고 실행을 시도한다.

    사람의 확인 요청과 결과를 대조한다

    파일, 변경 내용, 실행 결과를 직접 살펴본다.

    에이전트라는 이름은 “항상 스스로 완벽하게 끝낸다”는 뜻이 아니다. 작업을 여러 단계로 이어 갈 수 있다는 뜻에 가깝다. 계획이 틀릴 수도 있고, 보지 못한 파일이 있을 수도 있으며, 명령이 실패할 수도 있다. 그래서 코딩 에이전트의 장점은 사람의 확인이 사라지는 데 있지 않고, 확인할 수 있는 파일과 실행 흔적을 남기며 반복 작업을 돕는 데 있다.

    이번 리포트에서 다루는 범위

    이번 영상은 코딩 에이전트의 뜻, 작업 흐름, 사람과 에이전트의 역할, 결과 확인 방법만 다룬다. VS Code와 Codex 확장 기능을 실제로 설치하는 일은 영상 3에서 진행한다. KODEX 200 가격을 내려받아 CSV와 노트북을 만드는 일은 영상 4에서 직접 실행한다. Python 문법, 데이터 품질 판단, 매매 규칙, 백테스트도 이번 영상의 범위가 아니다.

    핵심 본편 · core

    대화형 응답과 에이전트 작업은 남는 결과가 다르다

    같은 AI라도 요청 방식과 작업면에 따라 다르게 일한다

    “챗봇”과 “코딩 에이전트”를 서로 완전히 다른 제품으로 외우면 오히려 헷갈린다. 같은 AI 서비스도 대화창에서는 설명을 주고받는 데 집중할 수 있고, 코드 편집기와 작업 폴더에 연결되면 파일을 고치고 명령을 실행하는 에이전트처럼 일할 수 있다. 중요한 차이는 제품 이름이 아니라 무엇을 보고, 무엇을 바꾸며, 무엇을 결과로 남기는가다.

    대화형 응답만 받을 때는 사용자가 코드를 복사하고, 파일 위치를 고르고, 실행하고, 오류를 다시 전달해야 한다. 에이전트 작업에서는 AI가 허용된 폴더를 살펴보고 파일을 고친 다음, 명령을 실행해 오류를 읽고 수정할 수 있다. OpenAI는 Codex를 작은 요청에 실시간으로 협업하는 방식과 더 긴 작업을 맡아 수행하는 방식에 모두 쓰는 코딩 에이전트로 설명한다 (Introducing upgrades to Codex).

    표 1제품 이름이 아니라 작업 문맥·행동·결과물로 구분한 두 사용 방식.
    구분 대화형 응답에 머무를 때 코딩 에이전트로 작업할 때
    주로 보는 것 사용자가 붙여 넣은 질문과 자료 질문, 열린 파일, 선택 영역, 작업 폴더의 관련 파일
    주로 하는 일 설명·예시 코드 제안 파일 탐색·수정, 명령 실행, 오류 확인, 재수정
    남는 결과 대화 내용 대화 내용, 실제 파일, 변경 내역, 실행 기록
    사람이 할 일 코드를 옮기고 실행하는 일까지 직접 수행 작업 목표를 정하고 변경과 실행 결과를 검토

    이 표는 대화형 AI가 파일을 절대 다루지 못한다거나 코딩 에이전트가 늘 명령을 실행한다는 제품 분류표가 아니다. 한 작업 안에서도 먼저 설명을 듣고, 계획을 고친 뒤, 파일 변경을 허용할 수 있다. 사람은 작업의 위험과 준비 상태에 따라 어느 단계까지 맡길지 정한다.

    핵심 본편 · core

    에이전트는 작업 폴더를 보고 고치고 실행하며 반복한다

    작업 문맥은 에이전트가 현재 볼 수 있는 재료다

    문맥(context) 은 에이전트가 이번 작업을 이해할 때 참고하는 정보다. 사용자의 요청, 현재 연 파일, 선택한 코드, 폴더 안의 안내 문서와 기존 파일이 여기에 들어갈 수 있다. Codex IDE 확장 기능은 열린 파일과 선택 영역을 대화에 붙일 수 있고, 같은 화면에서 변경 요약과 차이를 검토하게 한다 (Codex IDE 확장 기능 공식 문서).

    문맥은 많기만 하면 좋은 것이 아니다. 다른 종목의 오래된 노트북, 관계없는 데이터 파일, 서로 충돌하는 지시가 함께 들어가면 엉뚱한 기준을 따를 수 있다. 초보자는 “내 컴퓨터 전체를 AI가 다 안다”고 생각하기 쉽지만, 실제로는 현재 열어 준 프로젝트와 전달한 정보 안에서 판단한다고 이해해야 한다.

    한 번의 대답보다 반복 고리가 중요하다

    코딩 에이전트는 보통 요청을 읽고 바로 최종 파일 하나를 내놓지 않는다. 관련 파일을 찾고, 계획을 세우고, 파일을 고치고, 명령을 실행한 뒤, 실패하면 원인을 읽고 다시 수정한다. OpenAI의 prompting 공식 문서도 버그 수정 예시에서 재현 절차와 제약을 먼저 주고, 수정 뒤 같은 절차와 관련 검사를 다시 실행하도록 권한다 (Prompting Codex).

    이 고리에서 명령(command) 은 컴퓨터에 시키는 구체적인 실행 지시다. 예를 들어 Python 파일을 실행하거나 테스트를 돌리고 폴더 안의 파일 목록을 확인하는 일이 명령이다. 명령이 성공했다는 사실은 해당 명령이 오류 없이 끝났다는 뜻일 뿐, 투자 목적이 옳거나 데이터가 정확하다는 뜻은 아니다.

    표 2에이전트의 행동을 사람이 확인할 수 있는 흔적과 연결한 표.
    에이전트의 행동 화면이나 파일에 남아야 할 흔적 사람이 확인할 질문
    관련 파일을 찾는다 읽은 파일 이름과 작업 범위 관계없는 폴더까지 보지 않았는가
    파일을 만든다·고친다 새 파일과 변경 전후 차이 요청한 이름과 내용이 맞는가
    명령을 실행한다 실행한 명령과 종료 결과 필요한 검사를 실제로 실행했는가
    오류를 수정한다 실패 원인과 수정 내역 증상을 숨기지 않고 원인을 고쳤는가
    완료를 보고한다 산출물·검사·남은 한계 요약 보고와 실제 결과가 일치하는가
    핵심 본편 · core

    좋은 작업 요청은 목적과 범위와 확인 방법을 함께 말한다

    Python 문법 대신 원하는 결과를 구체적으로 말한다

    코딩을 모른다고 해서 아무 말이나 짧게 던져도 된다는 뜻은 아니다. Python 문법은 몰라도 무엇을, 어디에서, 어떤 파일로 만들고, 어떻게 확인할지는 투자자가 정할 수 있다. OpenAI의 Codex prompting 문서는 유용한 요청에 원하는 동작, 관련 코드나 재현 절차, 지켜야 할 제약, 변경을 확인하는 방법이 들어간다고 설명한다 (Prompting Codex).

    다음 예시는 영상 4에서 사용할 KODEX 200 작업을 설계만 해 보는 것이다. 아직 패키지를 설치하거나 가격을 내려받지 않는다.

    표 3짧지만 모호한 요청을 확인 가능한 작업 요청으로 바꾸는 세 가지 예.
    빠진 요청 왜 모호한가 고쳐서 말할 내용
    “KODEX 200 차트 만들어 줘” 종목코드·기간·저장 위치·완료 조건이 없다 069500, 날짜 범위, CSV와 노트북, 표와 종가 그래프를 지정한다
    “알아서 좋은 방식으로 해 줘” 에이전트가 데이터 경로와 파일 구조를 임의로 고른다 현재 작업 폴더만 쓰고 계획을 먼저 설명하라고 한다
    “됐으면 알려 줘” 무엇을 확인해야 완료인지 알 수 없다 만든 파일, 실행 명령, 결과, 남은 한계를 보고하게 한다

    한 번에 완벽한 요청을 쓸 필요는 없다. 먼저 계획만 부탁하고, 빠진 항목을 확인한 다음, 파일 변경을 허용해도 된다. 중요한 것은 에이전트가 임의로 채운 결정을 사용자의 결정으로 착각하지 않는 것이다.

    읽기 포인트

    영상 4에서 사용할 작업 요청의 뼈대: 현재 강의 폴더 안에서만 작업한다. KODEX 200 069500의 정해진 기간 가격을 로컬 CSV에 저장하고, 노트북이 그 CSV를 다시 읽어 표와 종가 그래프를 표시하게 한다. 먼저 계획과 필요한 파일을 설명하고, 끝나면 만든 파일·실행 방법·확인 결과·남은 한계를 보고한다.

    이 문장은 수익 전략을 만들어 달라는 요청이 아니다. 데이터 파일과 표시 노트북을 만드는 작업만 정의한다. 어떤 때 사고팔지, 결과가 수익성이 있는지 판단하는 일은 들어 있지 않다.

    심화 부록 · deep

    사람은 방향을 정하고 에이전트는 실행 가능한 일을 맡는다

    일을 나누면 책임도 선명해진다

    코딩 에이전트를 잘 쓴다는 것은 모든 일을 맡긴다는 뜻이 아니다. 사람은 투자 대상과 목적, 허용 범위, 완료 조건을 정한다. 에이전트는 그 범위 안에서 파일을 살피고 코드를 만들고 실행한다. 마지막에는 사람이 변경 내용과 실행 결과를 보고 받아들일지, 고칠지, 되돌릴지 정한다.

    OpenAI도 에이전트가 만든 변경을 적용하거나 배포하기 전에 사람이 검토할 것을 권하며, Codex의 로그와 테스트 결과를 그 검토를 돕는 근거로 설명한다. 코드 리뷰 기능 역시 사람의 리뷰를 없애는 대체물이 아니라 추가 검토자로 쓰라고 밝힌다 (Introducing upgrades to Codex).

    표 4사람과 에이전트가 맡을 일을 목표·범위·구현·검증·최종 결정으로 나눈 표. 이 역할 구분은 AIML Quant의 학습용 기준이다.
    판단과 작업 사람이 책임진다 에이전트가 돕는다
    목표 어떤 종목·기간·결과물이 필요한지 정한다 목표를 실행 단계로 나누어 제안한다
    범위 어느 폴더와 어떤 명령까지 허용할지 정한다 허용된 범위 안에서 파일과 도구를 사용한다
    구현 중요한 금융 가정과 완료 조건을 확인한다 코드와 파일의 초안을 만들고 오류를 고친다
    검증 결과가 요청·데이터·투자 목적과 맞는지 판단한다 실행 기록과 검사 결과를 모아 보고한다
    최종 결정 수락·수정·되돌리기·중단을 결정한다 후속 요청에 따라 다시 작업한다

    퀀트 작업에서는 이 구분이 특히 중요하다. 에이전트가 종가 그래프를 정확히 그렸더라도 그 그래프가 매수 근거가 되는지는 결정할 수 없다. 데이터가 미래 정보를 섞었는지, 전략 규칙이 투자 아이디어를 제대로 표현했는지, 손실 위험을 감수할 수 있는지는 별도의 금융 판단이다.

    심화 부록 · deep

    완료 보고는 출발점이고 실제 파일과 실행 결과가 증거다

    “완료했습니다”라는 문장을 그대로 믿지 않는다

    에이전트의 마지막 답변은 작업 결과를 찾기 쉽게 요약한 보고다. 그 문장 자체가 성공의 증거는 아니다. 파일이 실제로 생겼는지, 변경한 줄이 요청과 맞는지, 명령을 실행했는지, 표와 그래프가 나타나는지 차례로 확인해야 한다.

    OpenAI의 IDE 문서는 변경 요약과 실제 수정된 줄을 함께 보고, 원하는 변경만 남기며, 필요하면 같은 대화에서 다시 요청하라고 안내한다. 첫 작업 전후에 Git 체크포인트를 만들어 되돌릴 수 있게 하라는 권고도 포함한다 (Codex IDE 확장 기능 공식 문서). Git은 파일의 변경 이력을 기록하는 도구다. 영상 3에서는 설치와 실행 환경에 집중하고, Git의 자세한 사용법은 이후 보충 자료에서 다룬다.

    확인은 다음 순서면 충분하다.

    1. 파일 — 요청한 이름과 위치에 실제 파일이 있는가.
    2. 변경 내용 — 새로 들어간 내용이 요청한 범위를 벗어나지 않았는가.
    3. 실행 기록 — 에이전트가 말한 명령을 실제로 실행했는가.
    4. 화면 결과 — 표, 그래프, 오류 메시지를 내가 직접 볼 수 있는가.
    5. 요구 조건 — 종목, 기간, 파일 형식, 표시 내용이 처음 요청과 같은가.

    테스트가 통과해도 모든 요구가 맞는 것은 아니고, 화면이 그럴듯해도 데이터가 맞는 것은 아니다. 각 증거는 서로 다른 질문에 답한다. 영상 4에서는 노트북을 처음부터 다시 실행해 파일과 화면 결과가 우연한 실행 순서에 기대지 않는지도 확인한다.

    심화 부록 · deep

    권한은 작업에 필요한 만큼만 열어 준다

    에이전트가 할 수 있는 일과 해도 되는 일은 다르다

    코딩 에이전트는 명령을 실행할 수 있으므로 편리하지만, 그만큼 작업 경계를 먼저 정해야 한다. Codex의 공식 prompting 문서는 로컬 명령이 파일과 네트워크 접근을 제한하는 샌드박스 안에서 실행되고, 그 경계를 넘어야 할 때는 사용자의 승인 정책을 따른다고 설명한다 (Prompting Codex). OpenAI의 실제 운영 사례도 낮은 위험의 일상 작업은 정해진 경계 안에서 처리하고, 위험이 커지는 행동은 사람의 검토에서 멈추게 하는 원칙을 설명한다 (Running Codex safely at OpenAI).

    이 과정의 첫 실습에서는 강의 전용 폴더 안에서만 파일을 만들고 고친다. 비밀번호, API 키, 증권사 인증 정보는 프롬프트나 노트북에 넣지 않는다. 에이전트에게 실제 주문 전송을 맡기지 않고, 삭제처럼 되돌리기 어려운 작업도 하지 않는다. 인터넷에서 데이터를 받아야 하는 영상 4에서는 어떤 사이트와 패키지를 쓰는지 계획을 먼저 보고 승인한다.

    읽기 포인트

    안전 원칙: 편리함은 권한을 넓게 주는 데서 나오지 않는다. 작업 폴더, 필요한 파일, 필요한 명령을 좁혀 주면 결과를 확인하고 되돌리기도 쉬워진다.

    이 리포트의 정의와 한계

    “AI 모델 + 문맥 + 도구 + 확인 반복”은 여러 제품에 적용되는 국제 표준 정의가 아니라, Codex의 공식 기능을 초보자가 이해하도록 AIML Quant가 정리한 학습용 구조다. 제품의 기능과 화면은 바뀔 수 있으므로 영상 3을 촬영할 때 설치 방법과 권한 화면을 다시 확인한다.

    OpenAI가 공개한 내부 개발 사례는 사람이 목표와 검증 기준을 정하고 에이전트가 구현을 수행하는 작업 방식을 보여 준다. 다만 그것은 특정 조직과 개발 환경의 사례이지, 모든 초보자나 모든 투자 작업에서 같은 생산성이나 품질이 나온다는 증거는 아니다 (Harness engineering).
